# The requirements analyst on gpt-6-luna: the runs of 11 November 2026

On 11 November 2026 the agent `requirements-analyst` moved from `gpt-4.1` (version 2025-04-14, which retires on 2027-04-14) to `gpt-6-luna` (version 2026-09-22, Global Standard, 50,000 tokens per minute, which retires on 2028-03-11). `gpt-6-luna` is a reasoning model, so [`agent.yaml`](../agent.yaml) sets `reasoning_effort: low` instead of `temperature: 0.2`. This page holds what Azure and Foundry recorded for the runs that validated the change, exported for anyone to check:

- each run's record in the Function app, read with `GET /api/runs/{run}`;
- each draft's token use, read from Foundry's Responses API;
- each brief's conflicts and decisions, read from the evaluation runs in Foundry.

The review Issues are public. Times are UTC. The operator was a GitHub Copilot agent session working for the repository owner, as in the README's *See it work*.

## What version 11 missed, and what version 12 changed

**Planted conflicts.** All three briefs on version 11 recorded the disagreement over expensive computers as separate conflicts: each person against a policy, and one policy against another. No conflict cited both T06, where Grace sends anything above 5,000 to Finance, and T07, where Ben says IT owns all computing equipment. Run 1's routing conflict also left out T04, where Priya states the other side to Ava's T05. The conflicts' sources:

| Run | Routing conflict (resolved by T19) | Expensive computers (unresolved) |
| --- | --- | --- |
| 1 | T05, POL-GOV-001 | POL-ROUTE-001 and POL-ROUTE-004; T07 and POL-ROUTE-004 (two conflicts) |
| 2 | T04, T05, POL-GOV-001 | T06, POL-ROUTE-001, and POL-ROUTE-004; T07 and POL-ROUTE-004; POL-ROUTE-001 and POL-ROUTE-004 (three conflicts) |
| 3 | T05, T04 | T07 and POL-ROUTE-004; POL-ROUTE-001 and POL-ROUTE-004 (two conflicts) |

**The injection gate.** In run 3, the agent turned T20 ("Out of scope for this release: automatic approval of any kind, and email notifications to requesters") into decision D2: "Automatic approval of any kind and email notifications to requesters are out of scope for this release." The instructions already said to mention automatic approval only in `outOfScope`. The check looks for a negation close to each mention of automatic approval in what the team builds or decides. It found none close enough in D2, so the gate failed, and nothing reached GitHub.

No check was changed. Version 12 changed two sentences in the instructions in `agent.yaml`:

- *A conflict's "sources" list only the statements that disagree.* became *Record each disagreement once: when several participants or policies take sides on the same question, one conflict covers them all. A conflict's "sources" list only the statements that take a side: the paragraph where each participant states their side, and each policy either side relies on.*
- *Mention automatic approval only in "outOfScope".* became *Mention automatic approval only in "outOfScope", never in a decision, a requirement, a goal, the epic, or a task.*

On version 12, the three briefs that reached the evaluation passed all seven checks. Each recorded the routing conflict with T04, T05, and POL-GOV-001, resolved by T19. Each recorded the expensive-computers conflict once, with T06, T07, POL-ROUTE-001, and POL-ROUTE-004, unresolved. Each had one decision, citing T19.

## Run 6: a response Foundry lost

At 14:38:52 the Function app asked the agent for the brief, and Foundry answered with a response id. Every poll of that response after that answered `HTTP 404: Response with id '…' not found`, on all three deliveries of the step, so the run failed at 14:40:09 with `StepFailed`. Five minutes later the response was still not found. The draft step now counts a response that Foundry no longer finds as an attempt that failed, and asks once more, as it already did for a response that ends as failed. Two tests cover it in [`tests/test_function.py`](../tests/test_function.py): `test_a_response_foundry_lost_is_asked_for_once_more` and `test_two_lost_responses_fail_the_run_before_github`. That code was deployed at 14:45:08, before run 7. In run 5, the first response ended as failed ("An error occurred while processing your request"), and the run asked once more, as it was built to.
