## The change

STD-SEC-002 says: *Send AI services only the fields the use case needs. Attachments and personal data must not be sent.* E04's label lists the claims a right answer may state, and one of them is enough. Two were added, in [`eval_cases.jsonl`](../eval_cases.jsonl):

| E04's `states` | Claims |
| --- | --- |
| Before | `only* field*`, `minimal* payload`, `minimum* field*`, `minimal* field*`, `minimum* payload` |
| After | the same five, `minimi* set of field*`, and `allowlist* field*` |

A claim's words must come in order, in one clause, with at most three other words between one and the next (`CLAIM_GAP` in `checks.py`). Read by today's `checks.py` with the new label:

| Phrasing | E04's states |
| --- | --- |
| *Send a minimized set of fields.* / *Minimize the set of fields you send.* | stated |
| *Keep an allowlist of fields for triage.* / *Allowlist the request fields triage needs.* / *Allowlisted fields only go to the model.* | stated |
| *Use a minimized, explicitly allowlisted set of fields.* | stated, by `allowlist* field*`: the comma ends *minimized*'s clause |
| *The request fields are allowlisted.* | not stated: the words come in the other order |
| *Minimize the number of personal data fields.* | not stated: `minimi*` needs *set of fields*, and STD-SEC-002 doesn't minimize personal data, it excludes it |
| *Do not allowlist fields; send the whole request.* / *Rather than a minimized set of fields, send everything.* | not stated: denied |
| *Allowlist fields, including attachments.* | stated, but fails on `includ* attachment*` in `rejects` |

E04's `rejects` and `evidence`, the other cases, the held-out cases, and `checks.py` are unchanged. Its negation scope is unchanged too: a negation word anywhere in a clause still denies every claim in that clause.

### The answer that changed

`gpt-6-luna`, agents version 8, the standards run's `evalrun_c2fc4f24ab4a4ec882796c255c56ab5c`. Under the old label, grounding failed with *conclusion: states none of 'only\* field\*', 'minimal\* payload', 'minimum\* field\*', 'minimal\* field\*', 'minimum\* payload'*. Under the new label it passes all five checks: `allowlist* field*` matches *explicitly allowlisted set of fields* in the recommendation.

> **Summary:** The standards do not name specific RequestHub fields. They require sending only fields needed for the use case and expressly prohibit sending attachments and personal data. Whether particular fields qualify as necessary must be established for RequestHub’s use case. There is a conflict between the rule against persisting user free text in raw prompts/completions and a rule requiring full prompt/completion logging.
>
> **Recommendation:** Use a minimized, explicitly allowlisted set of fields shown to be necessary for triage; exclude attachments and personal data. Do not assume a field is allowed merely because it exists on the request. Document the data flow in the ADR. Resolve the prompt/completion logging conflict with an architect before deciding what to log or persist. The standards do not specify which individual RequestHub fields are necessary, so that allowlist remains to be determined.

### The misread that stays

`gpt-6-luna`, agents version 4, `evalrun_a8fea5390618422d938a2d5f96b6d571`, also a right answer, fails grounding under both labels:

> **Summary:** Attachments must not be sent. For other request data, send only fields the use case needs and exclude personal data; the retrieved standards do not name a field-by-field allowlist. The standards conflict over prompt/completion logging: one forbids persisting raw prompts or completions containing user-entered free text, while another requires logging the full prompt and completion for 30 days. An architect must resolve that conflict before deciding how prompts and completions are handled.
>
> **Recommendation:** Do not send attachments or personal data. Define a use-case-specific set of necessary, non-personal fields; the standards do not identify which RequestHub fields meet that test. Before implementation, an architect must resolve the prompt/completion logging conflict. If the AI feature proceeds, record the provider response or trace identifier correlated with the business record, use managed identities or workload identity federation, and route production model calls through the central AI gateway (Azure API Management). Keep AI output advisory; approvals and rejections require a human decision. Document the data flow in the ADR.

Its *only fields* sits in a clause with *exclude*, the negation scope that stays as it is, and the comma in *a use-case-specific set of necessary, non-personal fields* ends a clause before *fields*. A claim `set of necessar*` would have passed it, and no other stored answer would have changed, but without *fields* it also states E04's conclusion for *Send the model a set of necessary attachments*, a wrong answer the new label fails. So it wasn't added.

### A gap the change doesn't close

E04's `rejects` don't catch an answer that adds the attachments after the fields: *Send only the fields triage needs plus the attachments* passes the old label, and *Send a minimized set of fields plus the attachments* passes the new one. The `states` claims can't close that; a reject such as one for *plus the attachments* would, as a separate change.
